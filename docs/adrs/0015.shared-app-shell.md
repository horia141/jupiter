# ADR 0015: One shared shell for the desktop and mobile apps

## Status

Accepted (2026-10-11)

## Context

The desktop (Electron) and mobile (Capacitor) apps are thin shells around the
WebUI: they show a loading page, load a server's WebUI, and show an error page
when that fails. Both also let people pick a self-hosted server instead of the
official one.

Each app had its own hand-copied pages, styles and loader, and its own server
check. The copies had drifted: desktop defaulted a bare address to http while
mobile used https, the two reported errors differently, a 5xx was handled
three different ways across desktop, iOS and Android, and the desktop picker
lived on the server, so it was out of reach exactly when the picked server was
down.

## Decision

- **One package, `@jupiter/shell` (`src/shell`).** It holds the loading, error
  and server picker pages, `shell.css`, and the server check. Each app's
  `vite.config.ts` calls `shellViteConfig` to build the pages into its own
  `dist`.
- **A thin adapter per app.** The pages reach the platform only through a
  module each app supplies, aliased as `#adapter`: `src/desktop/src/adapter.js`
  (IPC to the main process) and `src/mobile/src/adapter.js` (Preferences and
  `CapacitorHttp`). `src/shell/pages/shell.js` lists what an adapter exports.
- **One server check.** `checkServer` in `src/shell/lib/check-server.js` is pure
  and unit tested; each platform passes the HTTP call it should use. Plain
  `http://` servers are allowed only in local builds.
- **The picker lives in the shell.** The WebUI's `/app/pick-server` route only
  hands over to it: through IPC on desktop (a server page can't navigate to
  `file://`), and by navigating to Capacitor's local origin on mobile.
- **The official server is never saved.** With nothing saved, an app follows
  the server its build points at. Development runs of the desktop app (not
  packaged) never save one at all: they are aimed at an instance whose port
  changes between runs, so a saved server would go stale.
- **Every failure lands on the shell's error page**: a timeout, a failed
  connection, and a 5xx. Desktop watches `did-navigate`; iOS wraps Capacitor's
  navigation delegate (`ShellViewController.swift`); Android swaps in its own
  `BridgeWebViewClient` (`MainActivity.java`). A 4xx is left to the WebUI.
- **Shells list their features in the frontdoor URL** (`shellFeatures`), like
  the rest of what they tell the WebUI about themselves. The WebUI relies on a
  feature only when it is listed, so older app builds keep working.
- **On mobile, links to other sites open through `@capacitor/browser`**, when
  the shell lists `external-browser`.

## Consequences

- Visual and behavioural changes to the shell pages are made once, in
  `src/shell`, and show up in both apps.
- The desktop main process imports `@jupiter/shell` at runtime, so
  `tasks/build/desktop.sh` copies it into `node_modules` before packaging, as it
  does for `@jupiter/webapi-client`.
- Self-hosted servers need https for the apps.
- Desktop keeps loading other origins in the same window, because Google and
  Apple sign-in navigate there and back. Only links that open a new window go
  to the system browser.
- A new shell capability needs a `ShellFeature` value, an entry in the shells'
  `FRONTDOOR_PATTERN`, and a `hasShellFeature` check in the WebUI.
