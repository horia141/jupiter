# ADR 0008: Backend blend controlled via `Config.global`

## Status

Accepted (2026-05-03)

## Context

Backend processes wire several replaceable infrastructure pieces: authentication
provider, telemetry sink, CRM integration, domain persistence, and search.
Operators need a single, explicit place to choose that **blend** per deployment,
without scattering ad hoc rules across `env`, hosting flags, and implicit
defaults.

## Decision

1. **Control surface**  
   Environment variables live in `src/Config.global` (loaded with other
   universe-wide settings when building global configuration). Together they
   define the **backend blend** for WebAPI, WebUI, API, MCP, and cron workers
   that share the same deployment.

2. **Global scope**  
   Global blend values apply to **all** processes in a deployment that load
   `Config.global`, not per workspace, user, or request.

3. **Variables and allowed values**

   | Variable | Allowed values | Meaning |
   | -------- | -------------- | ------- |
   | `AUTH_PROVIDER` | `local`, `local-google-apple` | Authentication backend. `local-google-apple` enables both Google and Apple sign-in |
   | `EMAIL_VERIFICATION_STRATEGY` | `none`, `verify` | Whether new users must verify email (`none` marks them verified at signup) |
   | `TELEMETRY` | `sentry`, `local` | Telemetry sink (e.g. Sentry vs local/no-op style) |
   | `CRM` | `wix`, `noop` | CRM integration vs no-op |
   | `LOCATION_RESOLVER` | `noop`, `google-maps` | External location suggestion backend (all services) and matching WebUI/Published widgets. `noop` returns no candidates; `google-maps` uses Places Autocomplete server-side and shows the Places search widget plus map views (same blend-gating style as `AUTH_PROVIDER=local-google-apple` for Google/Apple sign-in) |
   | `WEBAPI_STORAGE_ENGINE` | `sqlite`, `postgres`, `remote-postgres` | Primary domain persistence engine (WebAPI). `remote-postgres` uses an external connection string (dev tooling: `--webapi-postgres-url`) instead of a local sidecar. |
   | `WEBAPI_SEARCH` | `sql`, `algolia` | Search query / document storage engine (WebAPI) |
   | `WEBAPI_EMAIL_SENDER` | `noop`, `resend` | Email sender for verification messages (WebAPI) |

   Values are lowercase string tokens. Invalid or missing values should be
   rejected at startup with a clear error once wiring reads these variables.

4. **Credentials and URLs**  
   Provider-specific secrets and connection strings remain in service-level
   config (for example `src/webapi/srv/Config.project` and related env). The
   blend flags only choose **which** implementation to construct; they do not
   replace DSNs, API keys, or database URLs.

   `local-google-apple` reads provider credentials from service config, not from
   this blend table. Google uses `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and
   `GOOGLE_REFRESH_TOKEN_ENCRYPTION_KEY`. Apple uses `APPLE_TEAM_ID`,
   `APPLE_KEY_ID`, `APPLE_SERVICES_ID`, `APPLE_PRIVATE_KEY` (PEM contents of the
   Sign in with Apple `.p8` key), and `APPLE_REFRESH_TOKEN_ENCRYPTION_KEY`.

   The mobile app signs in through the native Google and Apple SDKs instead of
   a redirect (the system browser can't hand the session back to the WebView).
   The SDK returns an authorisation code, which the backend exchanges like the
   web one but with no redirect URI: Google's `serverAuthCode` goes to the same
   web client, and Apple's code goes to the app's bundle id (`BUNDLE_ID` from
   `Config.global`) as its client id. The WebUI also reads `GOOGLE_CLIENT_ID` and
   `GOOGLE_IOS_CLIENT_ID` (public values) to initialise the Google SDK.

   The app only offers a provider where the platform has a native SDK: Google on
   iOS and Android, Apple on iOS only. Android has no native Sign in with Apple
   (the plugin falls back to a web flow in a Custom Tab, which needs a deep link
   and a one-time code to hand the session back), and Apple only requires it on
   iOS, so we don't offer Apple in the Android app. An account created with
   Apple has no other login method, so such a user on Android signs in through
   the web app in a browser. Revisit this if that turns out to matter.

   Frontend blend exposure follows the Google auth pattern: WebUI and Published
   read the blend token from `Config.global` into `GlobalPropertiesContext`.
   `LOCATION_RESOLVER=google-maps` is what shows map views and the Places search
   widget. Each frontend service loads its own browser-restricted
   `GOOGLE_MAPS_API_KEY` from `Config.project` / `Config.project.secret` into
   service properties. The WebAPI key stays server-side for Places Autocomplete
   HTTP calls.

## Conventions by universe

- **Thrive** (`UNIVERSE=thrive`, hosted on Render): `AUTH_PROVIDER=local-google-apple`,
  `EMAIL_VERIFICATION_STRATEGY=verify`, `TELEMETRY=sentry`, `CRM=wix`,
  `LOCATION_RESOLVER=google-maps`,
  `WEBAPI_STORAGE_ENGINE=postgres`, `WEBAPI_SEARCH=algolia`,
  `WEBAPI_EMAIL_SENDER=resend`.
- **Other universes** (not thrive): local-first globals—`AUTH_PROVIDER=local`,
  `EMAIL_VERIFICATION_STRATEGY=none`, `TELEMETRY=local`, `CRM=noop`,
  `LOCATION_RESOLVER=noop` unless overridden, plus
  `WEBAPI_STORAGE_ENGINE=sqlite`, `WEBAPI_SEARCH=sql`.
- **Dev** (`UNIVERSE=dev`): no fixed convention; teams may set any valid
  combination while developing or testing.

## Consequences

- Operators set blend entries in `Config.global` (or equivalent injected env) for
  each deployment’s intended behavior.
- Composition code should branch on these settings (or on typed values derived
  from `JupiterGlobalProperties` / service properties) so behavior stays aligned
  with the declared configuration instead of re-deriving the same choices from
  unrelated signals.
